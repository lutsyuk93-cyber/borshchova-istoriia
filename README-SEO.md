# Борщова історія — GitHub Pages

## Що тут є
- статичний HTML/CSS/JS-сайт;
- SEO title/description;
- Recipe structured data на рецептах;
- robots.txt;
- sitemap.xml;
- 404.html;
- Google Analytics 4 (тег вже активний в усіх сторінках);
- сторінки рецепта, калькулятора порцій, видів борщу, подачі та порад.

## Сторінки сайту
- `index.html` — головний рецепт (Recipe structured data);
- `kalkulyator.html` — калькулятор інгредієнтів на кількість порцій (WebApplication structured data);
- `vydy-borschu.html` — огляд видів борщу (класичний, зелений, холодний, пісний тощо) — додатковий контент для охоплення ширшого кола пошукових запитів;
- `serving.html` — подача страви;
- `porady.html` — практичні поради;
- `404.html` — сторінка помилки.

## Англомовна версія (en/)
Сайт має паралельну англомовну версію в папці `en/` з тими самими
сторінками (`en/index.html`, `en/calculator.html`,
`en/types-of-borscht.html`, `en/serving.html`, `en/tips.html`,
`en/404.html`). У шапці кожної сторінки є перемикач `UA / EN`, що веде
на відповідну сторінку іншою мовою.

Для правильної індексації обох версій у Google в `<head>` кожної
сторінки додані теги `hreflang` (uk / en / x-default), а `sitemap.xml`
містить обидві мовні версії з переліком альтернатив. Якщо додаватимеш
нову сторінку — не забудь:
1. створити пару uk-версія / `en/`-версія;
2. додати взаємні `hreflang`-посилання в `<head>` обох файлів;
3. додати перемикач мов у навігацію;
4. додати обидва URL у `sitemap.xml`.

Плани для подальшого розширення контенту (не зроблено, для наступних ітерацій):
- окрема сторінка з детальним рецептом кожного виду борщу (зелений, холодний, пісний) з власною structured data;
- сторінка "Історія борщу" — походження страви, культурний контекст;
- сторінка з поширеними помилками під час приготування борщу.

## Публікація на GitHub Pages

1. Створи на GitHub public repository, наприклад `borshchova-istoriia`.
2. Завантаж у repository всі файли з цієї папки.
3. Відкрий `Settings` → `Pages`.
4. У `Build and deployment` вибери `Deploy from a branch`.
5. Branch: `main`, folder: `/ (root)`.
6. Натисни `Save`.
7. Після публікації відкрий адресу виду:
   `https://ТВІЙ-ЛОГІН.github.io/borshchova-istoriia/`
8. Після цього заміни в `robots.txt` і `sitemap.xml`:
   `lutsyuk93-cyber` → твій GitHub username
   `borshchova-istoriia` → назва repository.

## Google Analytics 4

У файлах HTML залишений закоментований шаблон Google tag.
Після створення GA4 Data Stream:
1. Отримай Measurement ID виду `G-XXXXXXXXXX`.
2. Розкоментуй блок Google Analytics у HTML.
3. Заміни `G-XXXXXXXXXX` на свій ID.
4. Завантаж зміни в GitHub.

Не вигадуй Measurement ID — використовуй той, який видасть Google Analytics.

## Після запуску
1. Перевірити сайт з телефону.
2. Підключити Google Search Console.
3. Додати sitemap.xml.
4. Перевірити індексацію.
5. Потім можна підключити власний домен.

GitHub Pages підтримує HTTPS для github.io-сайтів і custom domains.

## Безпека на GitHub Pages

Сайт статичний (без бекенду й бази даних), тому класичних вразливостей
(SQL-ін'єкції, злам сервера) тут немає. Головні ризики — інші:

1. **Репозиторій має бути public** для безкоштовного GitHub Pages —
   це нормально для сайту-рецепту, але не публікуй у цьому ж репозиторії
   нічого приватного (API-ключі, чернетки, особисті дані).
2. **Ніколи не комітити секрети.** Цей сайт не потребує жодних ключів
   API — GA4 Measurement ID (`G-XXXXXXXXXX`) не є секретом, його можна
   бачити в коді сторінки. Якщо в майбутньому додаси форми чи інтеграції
   зі сторонніми сервісами — не зберігай токени/паролі у файлах репозиторію.
3. **Увімкни двофакторну автентифікацію (2FA)** на GitHub-акаунті —
   це головний захист від злому самого репозиторію.
4. **Branch protection** для `main` (Settings → Branches) — якщо
   у проєкті колись з'явиться більше учасників, це запобігає випадковим
   або зловмисним прямим змінам без перевірки.
5. **HTTPS обов'язковий.** У `Settings → Pages` увімкни `Enforce HTTPS`
   (для github.io увімкнено за замовчуванням; для custom domain — увімкни вручну).
6. **Сторонні скрипти.** На сайті підключений лише Google tag
   (`googletagmanager.com`) — не додавай сторонні `<script>` з незнайомих
   джерел без перевірки, це найпоширеніший спосіб зараження статичних сайтів.
7. **Форми зворотного зв'язку** (якщо з'являться пізніше) варто підключати
   через перевірені сервіси (Formspree, Google Forms тощо), а не
   реалізовувати власний бекенд без досвіду в безпеці.
8. Регулярно перевіряй вкладку **Security → Dependabot alerts** в
   репозиторії — GitHub сам сповіщає про відомі вразливості, якщо вони
   виявляться у файлах конфігурації чи залежностях.
